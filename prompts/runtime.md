# 应用运行时 Prompt 规格

任务输入、输出示例、编排和校验规则见本文。系统消息只装配入口文档指定的模板。 [Prompt 入口](./README.md) · [运行时输出 JSON Schema](../docs/runtime-contract.schema.json)

### 系统消息与输入边界

每次调用按下文的装配规则组合公共约束、角色或任务模板、议题策略以及输出契约。应用将本场业务输入作为独立消息的序列化 JSON 传入。模板与 Schema 共同版本化。若上游支持原生结构化输出，可以附上该任务的 Schema，服务端仍按具体任务校验，避免误将其他任务的有效结构判为当前任务有效。接口协议、模型标识、可用输出格式及总时限以实际接入验证为准。

[查看 Prompt 模板](./common.md)

| 输入对象 | 固定字段与边界 |
| --- | --- |
| `topic`, `expertCount` | 主题去首尾空白并按业务规则校验。人数 `2–6`，默认 `4` |
| `discussionGoal`, `phase` | R02–R07 由应用传入固定类型与当前阶段。R01 读取题目、人数与允许的视角，返回新房间的目标。`phase` 在开场为 `OPENING`，总结为 `SUMMARY`，主持串联及追问使用将要开展或重新尝试的阶段 |
| `host`, `expert`, `allowedPerspectives`, `perspectives` | 运行时角色卡包含 `participantId`、`displayName`、`profession`、`title`、`stance`、`perspective`。主持 `stance=null`、`perspective=null`，专家提供自己的立场和视角。R01 用 `allowedPerspectives` 传入允许使用的视角，R05 用 `perspectives` 传入已选专家的视角值。六类视角依次是证据、交付、成本、风险、用户影响、治理 |
| `utterances` | 运行时任务收到的本场已提交 `{seq,participantId,speakerName,role,kind,content,replyToUtteranceSeq}[]`。序号为正整数且唯一，正文非空，成员、角色和发言类型须与本场记录一致。允许空数组的任务及截断算法见后文。整轮报名使用同一冻结版本与实录切片。 |
| `insights`, `previousInsights` | 已验证观点的 `{kind,text,evidenceUtteranceSeqs}[]`。保留引用信息。若观点暂缓，另传 `insightStatus` 及来源序号，不能按最新实时观点使用 |
| `replyToUtteranceSeq`, `proposal`, `mode` | 应用已验证并绑定的回应目标、R02 建议陈述、主持动作或总结模式。模型结果不可改变其来源或作用域 |
| `externalEvidence` | 仅 R03 接收。每条含 `title`、`url`、`excerpt`，表示已核验的来源标题、HTTPS 地址、连续原文。它和主题一样作为数据传入。没有可用资料时使用空数组 |

解析只接受完整的 UTF-8 JSON 对象。重复键、额外字段、尾随文本、非法空值及超限响应按结构错误处理。模型供应商若返回分离的正文和推理字段，只读取正文。公开 DTO 由服务端按白名单构建。`discussionId`、模板版本、游标、截止时间和幂等状态由服务器持有。

### 运行时输出契约速查

本表足以让持有单份 Markdown 的开发者重建任务 Schema。除 R02 的可选 searchQuery 和 searchPremise 外，表中列出的输出字段均必填，包括可空字段。所有对象均拒绝额外字段。文本长度按 Unicode 码点计。`seq` 和引用号均为正整数。自然句包含非空正文、无换行、仅句尾有一个中文句末标点 `。！？`。普通发言、开场和主持介入为 1–2 句，每句 2–120 码点，业务层验证总长不超过 120。总结每句 2–200 码点，两句合计不超过 200。仓库联调按对应 `$defs` 验证任务，R08 复用原任务定义。

| 任务及定义 | 输出字段、枚举和边界 |
| --- | --- |
| R01 `rosterOutput` | `discussionGoal` 取 `EVALUATE/PROPOSE/SOLVE/EXPLORE`。`participants` 为 3–7 项，第一项 `HOST`、其余 `EXPERT`。每项有 `role`、`displayName`（2–20）、`profession`（2–32）、`title`（2–40）、`stance`（专家 8–100）、`perspective`。主持两个字段均填 `null`，专家视角取 `EVIDENCE/DELIVERY/COST/RISK/USER_IMPACT/GOVERNANCE`。业务层按请求校验人数、规范化姓名及视角唯一。 |
| R02 `bidOutput` | `intent` 为 `RAISE/BUZZ/ADD/REBUT/PASS`。普通短台词可标记 `speechReady`。查证需同时给出 `searchReason` 和有效的 `searchQuery`。`targetUtteranceSeq` 在 `ADD/REBUT` 时为正整数，其余为 `null`。`focusCode`、`proposedClaim` 在 `PASS` 时为 `null`，其余分别为受控枚举及 2–80 码点的一句。关注枚举取 `TRADE_OFF/ASSUMPTION/EVIDENCE/RISK/IMPACT/IMPLEMENTATION`。 |
| R03/R05 `utteranceOutput` | `sentences` 为普通口播数组。 |
| R04 `insightsOutput` | `insights` 为 0–6 项。每项有 `kind`（`CONSENSUS/DISAGREEMENT`）、`text`（4–80）、`evidence`（2–4 项）。每项证据有 `utteranceSeq` 和 `quote`（4–120）。业务层限制每类最多 3 条，验证不同专家数、引用完整性与原文。 |
| R06 `interventionOutput` | 普通口播 `sentences` 与 `replyToUtteranceSeq`（正整数或 `null`）。业务层要求 `BRIDGE` 的目标为本次输入中的专家发言。 |
| R07 `summaryOutput` | `sentences` 为两句中立收尾，具体业务观点逐项归因于专家。`evidenceUtteranceSeqs` 为 0–6 个不重复的专家发言号。 |
| R08 | 复用当前任务的输出结构。`validationCodes` 只属于应用输入。 |

### 讨论目标识别与 Prompt 装配

R01 在一次回复中返回讨论目标及对应阵容。装配顺序、配置和自定义方式见运行时 Prompt 入口。 [装配规则](./README.md#模板装配) · [类型路由](./route.md)

服务端校验枚举和阵容后同事务保存 `discussionGoal` 与草稿。阵容预览和详情返回该字段，确认开始时由后端加载对应阶段表。旧记录缺类型时按 `EXPLORE` 迁移，新预设显式配置枚举。新模型响应缺字段或返回未知类型时走 R08 和阵容失败分支。`SOLVE` 与 `PROPOSE` 的专家可共享目标，Q01 依据可区分的原因假设、检查动作或实施路径判断实质差异。

服务端按房间已保存的 `discussionGoal` 加载阶段表。阶段段落只说明当前关注点：专家据此约束贡献方向，主持据此向专家提问，R04 据此排序关注点。三者都不得据此新增业务内容或改变角色边界。阶段切换无需额外模型调用。

### 阶段、报名窗口与调度配置

一个讨论阶段有特定目标，可包含多个报名窗口。每个窗口只裁决一个发言人，专家报名仍可并行。一次成功入库的专家发言消耗当前阶段一个发言名额，主持发言与结论提炼不消耗专家名额。下表是首版可配置默认值。

| 类型 | 正常阶段路径 | 各阶段发言上限 | 各阶段报名窗口上限 |
| --- | --- | --- | --- |
| `EVALUATE` | 比较标准 → 检验条件与反证 → 形成有条件建议 | 3 / 4 / 3 | 4 / 6 / 4 |
| `PROPOSE` | 提出路径 → 检验可行性 → 定义首轮试点 | 3 / 4 / 3 | 4 / 6 / 4 |
| `SOLVE` | 提出原因假设 → 设计区分性检查 → 确定行动优先级 | 3 / 4 / 3 | 4 / 6 / 4 |
| `EXPLORE` | 梳理不同视角 → 检验解释边界 → 衡量影响程度 | 3 / 4 / 3 | 4 / 6 / 4 |

后端启动时读取流程模板，按数组顺序执行阶段。每项的 `phase` 对应议题策略中的段落，`maxExpertTurns` 与 `maxWindows` 分别限制专家发言和报名窗口，`preferredFocusCodes` 的顺序决定加分。名额在房间开始时固定，剩余名额不随阶段转移。 [流程模板](./workflow.json)

1. **开场并冻结输入。** 确认后执行 R05，提交开场才进入第一阶段。每次实际启动 R02 窗口时消耗一个窗口名额，并冻结 `{discussionGoal, phase, windowNumber, contentVersion}`。同窗专家收到同一实录版本，只传各自角色卡。请求回调由后台任务核对窗口和内容版本，迟到结果无权参与下一窗或下一阶段。
2. **验证并集中裁决。** 排除 `PASS` 和不合格候选。有其他合格候选时，同一专家连续两次发言后让位。按 `意图权重 + 缺席加分 + 当前阶段关注点加分` 降序。意图权重为 `REBUT=3、ADD=2、BUZZ=2、RAISE=1`。缺席加分取自上次发言以来的专家发言数，上限 2，初次发言者按已完成发言数计。首选关注点加 2，其他配置项加 1，未列出的加 0。同分先选较久未发言者，再按稳定成员 ID 升序。模型只提供合法 `focusCode`，权重、分数和获选人由服务端计算。
3. **提交发言与提炼。** 仅就绪候选参与裁决。已校验的普通短台词获选后直接发布，其余候选使用 R03 扩写或整合预先取得的证据。成功写入专家发言后增加本阶段发言计数，再完成一次逻辑 R04 或发布暂缓。发言失败清理状态，已启动的报名窗口仍计入上限。当前阶段达到发言或窗口上限时推进下一阶段。
4. **处理无人报名。** 整窗可恢复故障且还有窗口和预算时继续报名，两窗连续无有效响应则按已有实录收尾。全员遇到鉴权、内容拦截等永久错误时进入 `FAILED`。至少有一条有效 `PASS` 但没有候选时，可在本阶段还有窗口、主持与模型预算充足时执行一次 R06 `FOLLOW_UP`，全场最多一次。追问失败也消耗这次机会，仍可在有预算时打开下一窗。追问后仍无人报名时推进下一阶段，给其他问题一次报名机会。没有可用追问时提前推进阶段。各阶段结束后仍不足两位发言专家时执行有限总结。部分模型失败单独计量。
5. **串联与收尾。** 切换到下一阶段时，若刚完成的阶段有已提交专家发言并且有预算，可执行一次 R06 `BRIDGE`，传入下一阶段目标。R06 中途任务默认三阶段合计最多三次逻辑调用，失败消耗额度，传输重试和 R08 计入物理请求数。计划执行完或达到全场预算时进入 `SUMMARIZING`。可见实录来自已提交记录，R07 在证据不足时返回有限总结。成功落库才完成讨论。

内置流程的常规配额合计 10 条专家发言、14 个报名窗口。末阶段设置 `reviewBeforeSummary: true` 后，常规配额用完且场内已有专家发言时，R02 收到 `closingReview=true`。每窗仅接纳指向其他专家已公开发言的 ADD 或 REBUT，提交后照常执行 R04，再开放下一窗。无合格回应时收尾，部分报名失败时向主持标记复核不完整。既有自定义流程可省略开关，以原阶段配额结束。默认全场时限 600 秒、物理请求上限 112 次，可另配显式发言硬上限。为 R07 保留 30 秒与两次请求。打开新窗口前给本窗首发请求预留 `专家数 + 2` 次，涵盖 R02 全员报名及成功入场后的 R03/R04。附加重试只能使用未预留额度。窗口结束后释放未使用名额。执行时限用各任务截止与收尾预留的较早者，触及全场收尾线时优先进入总结。若已提交新发言但本次 R04 超时，按暂缓规则先保留旧投影。R04 结果仍采用本场两位不同专家的真实引文，调度分数仅用于决定下一位发言者。

### 快照版本与结果提交

1. 在一个 SQLite 只读事务里按房间读取状态、成员、实录、结论和状态游标。以入库发言的最大 `seq`、最近一次 `insight.updated` 的事件序号（无则 `0`）标记内容版本。`lastEventSeq` 同时读取，用于诊断及前端快照，不作为模型任务的内容版本。小窗阶段等事件会推进 SSE 游标，并不会使实录内容过期。
2. 房间工作任务给每个逻辑步骤分配内部运行令牌、步骤号和截止时间。R02 同窗共享只读版本、讨论目标、阶段、规范化主题、主持提问、裁剪后的实录和结论。单个请求只替换本专家角色卡。按最大角色卡计算公共切片。内部调用记录保存 `discussionId`、运行令牌、阶段、窗口号、步骤号、尝试号、内容版本和本次允许引用集合，模型返回的标识一律拒绝。
3. 同一房间由编排器串行推进逻辑步骤，R02 可同轮并发。回包只写当前步骤的结果集合，首位合格候选就绪后最多再收集 350 毫秒再裁决，全员返回可立即裁决。回包先检查令牌、步骤、尝试号和截止时间。旧尝试、已关闭窗口、终态房间的结果直接丢弃。R08 使用原冻结业务数据（含 R03 的检索结果）与相同引用集合，新增的只有应用生成的校验编号。
4. 准备持久化时，在同一短写事务里复核预期房间状态及内容版本，确认当前步骤仍拥有提交权，再写业务行和事件。发言、投影或总结如果已经改变了内容版本，旧回包不覆盖新结果。合法的任务只允许成功提交一次。外部 HTTP 请求在数据库事务之外完成。

T02/T06/T08 用屏障重现两个版本交逆序返回。例如 R04 基于发言 4 发出，更新版本已处理发言 5 时才收到旧响应，旧响应既不能覆盖结论，也不能产生任何事件。阶段事件推进 SSE 游标但内容未变时，当前 R03 仍可正常提交。

### Token 预算与引用闭包

每次调用先算有效输入上限 `modelContextWindow - maxOutputTokens - 256`。`256` 为初始协议余量。用提供方计数接口或匹配模型的分词器，对系统指令、任务 Prompt、输出契约、消息包装、序列化输入及预留的 R08 错误码一起计量。输出初始预留分别为 R01 `2_304`、R02 `1_024`、R03/R05/R06 `640`、R04 `1_500`、R07 `768`、查证 `1_000` token；推理模型的思考 token 也计入该上限，因此保留余量并按真实截断率校准。通过 `reasoning_effort` 请求快速思考（默认 `low`，可配 `minimal`/`medium`/`high`），`off` 表示不发送该字段。使用已校准的保守估算时记录 `estimated`，上游明确拒绝上下文后按 `CONTEXT_UNAVAILABLE` 处理。输出截断时，唯一一次修正的输出上限可提升至原来的两倍，仍受剩余上下文和全场预算限制。

1. **确定必留项。** 保留题目、任务角色、最新主持提问（存在时）与已锁定的回应目标。R02、R03、R06 先保留最近 2 条专家发言，有几条保留几条。R04 和 R07 保留此版本的全部有效专家发言。R04 全量替换结论，核心实录必须足以覆盖该版本的全部专家发言。R01 与 R05 不装载历史。所有发言保留项均按第 3 步补齐回应链，结论单元也遵守同一规则。
2. **选择可随请求发送的结论。** 先选关联本轮目标或最新专家发言的结论，其次按证据最大 `seq` 降序、稳定 ID 升序，并取每类最多 3 条。每条结论与它引用的全部发言构成一个保留单元，按实际 JSON 重新计数后成组纳入。缺任一引用或单位放不下，就从模型输入省略该条结论。R04/R07 仍可依据完整专家实录重新判断。
3. **追加近期背景。** 用剩余预算按 `seq` 从大到小加入候选发言，一条包括其 `replyToUtteranceSeq` 所需的祖先记录。追溯到已有记录或空引用为止。缺失引用、循环、跨房间条目视为异常。对必留项，若目标无法验证则终止该任务。可选条目放不下时整组跳过。只有同时不属于必留项、没有被保留的结论引用、没有被保留发言的回应链引用的条目，才是可移除的非引用发言。原文整条保留，避免对句子做字节或 token 截断。
4. **冻结引用集合。** 按原始 `seq` 升序输出并去重，保留本场原编号及所有有效关系。用最终切片派生 `allowedUtteranceSeqs`，出参引用同时校验该集合、房间归属和冻结版本内的已提交记录。R03 的外部来源用剩余预算按条纳入，放不下时省略。只有完整的 R04 成功投影才能推进 `insightsThroughUtteranceSeq`，推进到处理的最新专家发言号。`lastEventSeq` 只随实际公开事件推进。两个游标均保持原始序号，前端快照和持久化实录不会因 Prompt 裁剪而变短。
5. **必留项超限时降级。** 先清空可选上下文重新计数。仍超限则不发模型请求，按任务降级。R04 置 `STALE` 并保留有效投影，R07 保留实录并按总结故障终止。本次没有生成候选结果，直接处理即可。

T08 样例。已有发言 `[1,2,3,4,5,6]`，R03 锁定目标为 `2`，最近两条专家发言为 `4/6`，`6` 回应 `4`，最新主持提问为 `5`。假设 `2/4/5` 没有回应目标且预算只允许 `[2,4,5,6]`，引用 `1` 的旧结论须从输入省略，独立旧发言 `3` 可移除。接受候选引用须同时满足任务的目标约束。`1/3` 不在本次引用集合，前端实录仍可读取全部六条。

### 模型、服务端与 SSE 字段归属

流程为模型生成候选 → 结构、安全和业务校验 → 服务端按版本提交业务记录与事件 → 前端消费。事件信封 `{discussionId,seq,occurredAt,payload}`、SSE `id` 和事件名全由服务端生成。SSE `id` 等于信封 `seq`。模型同名字段属于额外字段，不能参与写入或事件路由。

| 入口或事件 | 模型提供的候选 | 服务端生成或裁决的字段 | 前端消费规则 |
| --- | --- | --- | --- |
| 创建草稿响应 | R01 的 `discussionGoal` 与成员公开属性 | 校验并锁定讨论目标，生成 `id`、成员 ID、色板、`DRAFT`、时间与游标 | 阵容预览用响应快照展示类型与阵容，等待用户确认 |
| `discussion.status` | 无 | `status`、`startedAt`、`endedAt`、`errorCode`。确认、执行边界、故障与总结事务决定状态 | 更新直播及结束反馈。结束时保留已收到的内容，按终态关闭订阅 |
| `participant.status` | R02 合法 `focusCode` 可以映射 `publicFocus` | `participantId` 绑定调用身份。`stageStatus` 根据开始准备、取得模型槽、完成及清理推进。`publicFocus` 为映射后的标签或空值 | 更新专家窗。报名结果本身不触发 `SPEAKING`，只有相应服务端事件才切换焦点 |
| `utterance.added` | R03/R05/R06/R07 的 `sentences`，R06 可提出目标 | `payload.seq`、`participantId`、`kind`、`createdAt` 与合并后的 `content`。R03 沿用服务端锁定目标，R06 的目标由后端验证。R07 的内部证据数组不作为发言字段 | 按 `payload.seq` 追加实录。`SUMMARY` 同步显示于总结区，房间完成仍等待终态事件 |
| `insight.updated` | R04 的 `kind`、`text` 和待校验证据 | 观点 `id`、最终 `evidenceUtteranceSeqs`、`insightStatus` 和 `insightsThroughUtteranceSeq`。暂缓事件由应用保留旧结果后发出 | 整体替换投影。`STALE` 显示「观点更新暂缓」，沿用事件附带的有效观点和来源游标 |

浏览器以路由会话令牌、房间 ID、事件信封序号为应用条件。初次连接由详情 `lastEventSeq` 构造 `after`，重连优先使用 `Last-Event-ID`。序号小于等于已应用值时丢弃，出现缺号、信封与 SSE ID 不一致或有效载荷非法时重取一致快照。发言序号只用于实录和引用，结论来源游标只用于标识提炼覆盖范围。网络打开或关闭只改变连接提示。切房取消旧快照请求并关闭旧订阅，从终态快照进入时直接渲染。

```text
id: 18
event: utterance.added
data: {"discussionId":"room-a","seq":18,"occurredAt":"2026-11-19T02:00:10Z","payload":{"seq":6,"participantId":"expert-risk","kind":"EXPERT","content":"退出条款可以降低解约成本。","replyToUtteranceSeq":4,"createdAt":"2026-11-19T02:00:10Z"}}
```

T03/T06、E03/E04 用夹带状态、伪造房间和迟到回包的样本验证该边界。终止事务中的 `SUMMARY` 事件先于 `COMPLETED` 事件。提炼暂缓允许事件信封序号推进，结论来源游标保持不动。

### 输入脱敏与生成内容安全

| 检查位置 | 规则与处理 | 验收 |
| --- | --- | --- |
| HTTP 入口，任何外发模型请求前 | 校验 UTF-8 与请求体上限。主题按 NFC 统一 Unicode，制表符和换行合并为空格，去首尾空白。拒绝 NUL、其余控制字符及双向覆盖/隔离控制符 `U+202A–U+202E`、`U+2066–U+2069`。仅移除开头 BOM 与无语义的零宽空格 `U+200B`。保留中文标点、合法换行归一后的空格及 `C++` 等正常内容。用归一化后的有效主题校验 3–120 码点 | 正常中英文、Emoji 通过。NUL 或隐形方向覆盖返回 `400` |

展示和记录只使用经过校验的业务字段。检测可用归一化副本，证据比对始终使用已入库的公开文本。若旧公开发言包含需要脱敏的内容，整个记录不送入本次模型请求且不能引用。必留证据因此缺失时按上下文不可用处理。生产日志只记录规则编号、任务、跟踪 ID、计数、耗时及结果。专项证据检索若用于查证已有观点，外部资料属于补充参考，发布直播结论仍需本场两位专家的引文。 [证据检索规格](../.agents/skills/insight-evidence-retrieval/SKILL.md)

### R01｜阵容与不同决策视角

**任务标识** `R01`　**输出契约** `rosterOutput`　**触发条件** 用户提交新议题，请求通过服务端校验。  
**入参** `{topic,expertCount,allowedPerspectives}`。`topic` 为规范化及脱敏后的议题，`expertCount` 为应用确定的专家人数，`allowedPerspectives` 为本次允许使用的视角。  
**任务目标** 识别 `discussionGoal`，据此生成 1 位中立主持和 `expertCount` 位职责、判断依据和立场可区分的专家。解决 U01，支撑 F02。

[查看 Prompt 模板](./roles/roster.md)

**正常示例**　题目为「中小团队应优先自研还是采购 AI 客服？」，专家数为 `2`，允许视角包含 `COST` 和 `DELIVERY`。四周期限和规则变更频率在立场中都是假设条件。

```json
{
  "discussionGoal": "EVALUATE",
  "participants": [
    {"role":"HOST","displayName":"顾言","profession":"主持人","title":"科技议题主持人","stance":null,"perspective":null},
    {"role":"EXPERT","displayName":"陈简","profession":"成本管理","title":"成本控制负责人","stance":"优先控制上线成本，若需四周内交付且有退出条款则先采购，若解约成本超出预算则转向分阶段自研","perspective":"COST"},
    {"role":"EXPERT","displayName":"林昭","profession":"软件工程","title":"平台架构师","stance":"优先保留维护控制权，规则频繁变更时先自研编排层，若供应商支持规则导出且验证迁移可行则接受采购","perspective":"DELIVERY"}
  ]
}
```

#### 校验分支与验收

1. **输入分支。** 客户端提交的题目或人数非法时按参数错误处理。服务端构造的视角集合不足 `expertCount` 个有效值时，按配置或上下文错误处理，避免请求模型填补非法视角。R01 只接收本次创建的输入。
2. **强校验。** 核对枚举、唯一主持位置、请求人数、必填字段、规范化姓名唯一性、专家视角唯一性及其是否属于本次允许集合。唯一性比较使用规范化姓名，展示使用通过验证的 `displayName`。主持立场与视角必须为 `null`，专家立场须为有效文本。通过后由后端分配成员 ID 和色标，与草稿同一事务保存。
3. **低质量分支。** 视角标签不同但规范化立场相同，或立场只剩固定占位话术时，按 Q01 的确定性规则记为 `LOW_QUALITY`。近义重复由 Q01 语义评估核查，以主张、判断标准和转向条件判定。
4. **失败分支。** 首次结构或可修正业务错误按 R08 补偿。仍不合格则返回上游错误，草稿和阵容写入为零。页面保留本次表单，提供重试和预设入口。
5. **验收。** T01 覆盖人数、非法角色、规范化重复姓名、视角不在允许集合、主持带立场、专家缺少立场与低质量立场。断言请求无历史草稿或其他房间上下文，失败后无残留草稿、成员及事件。Q01 验证四种目标下专家选择及立场差异。

### R02｜一位专家的独立发言意愿

**任务标识** `R02`　**输出契约** `bidOutput`　**触发条件** 主持开场已经提交，编排器打开报名窗口并向每位专家发起独立调用。  
**入参** `{discussionGoal,phase,topic,expert,moderatorQuestion,utterances,insights,insightStatus,insightsThroughUtteranceSeq}`。同窗共享冻结实录、结论和当前阶段，每次只传一位当前专家的角色卡。  
**任务目标** 判断该专家有没有可推进当前讨论的一项贡献。合法候选交给服务端裁决。解决 U02，支撑 F03/F04。

[查看 Prompt 模板](./roles/expert-bid.md)

**正常示例**　评估进入检验条件阶段。发言 `#2` 的专家主张先采购包含编排的完整方案，本专家针对迁移限制提出反例。

```json
{"intent":"REBUT","targetUtteranceSeq":2,"focusCode":"RISK","proposedClaim":"采购完整方案可能加快上线，但核心编排无法导出时将抬高迁移成本。"}
```

**跳过示例**　当前专家只能重复已发表的观点。

```json
{"intent":"PASS","targetUtteranceSeq":null,"focusCode":null,"proposedClaim":null}
```

#### 校验分支与验收

1. **强校验。** 用房间、窗口和调用身份绑定专家，核对回包未过期、同一角色只有一个有效结果，以及 `intent`、目标、关注类别与候选陈述组合合法。`ADD/REBUT` 的目标须为本次输入中其他成员的发言，且 `REBUT` 只指向专家发言。依次将六种 `focusCode` 映射为「关注关键取舍」「检验前提假设」「关注证据依据」「关注风险与边界条件」「关注影响范围」「关注实施路径」。专家获选并进入实际准备阶段后，才向小窗发布对应公开标签。
2. **缺乏增量与失败分支。** `PASS` 是有效跳过，不进入候选排序。确切复述上一条发言、非法回指与格式错误可按对应原因进入 R08。候选修正仍失败时记录该专家调用失败，按窗口规则汇总，不能登记为主动 `PASS`。
3. **验收。** T02/T03 覆盖合法回应、自己发言、跨房间或已裁掉的引用、`PASS` 附带说明、乱序返回及旧窗口响应。Q02 核对意图是否与候选正文匹配，尤其是 `REBUT` 是否真的挑战被引用主张。

### R03｜选中专家的公开口播

**任务标识** `R03`　**输出契约** `utteranceOutput`　**触发条件** 候选经服务端裁决获选，已取得模型调用槽位。  
**入参** `{discussionGoal,phase,topic,expert,intent,moderatorQuestion,replyToUtteranceSeq,proposal,utterances,insights,insightStatus,insightsThroughUtteranceSeq,externalEvidence}`。`proposal` 来自已通过 R02 校验的 `proposedClaim`，`replyToUtteranceSeq` 为服务端绑定的回应目标或 `null`。  
**任务目标** 将入选贡献变成当前专家 1–2 句公开发言，保持承诺的意图、回应对象和实质增量。解决 U02、U03，支撑 F03/F06。

[查看 Prompt 模板](./roles/expert-speech.md)

**正常示例**　承接 R02 成功示例，`intent=REBUT`，服务端绑定 `replyToUtteranceSeq=2`。

```json
{"sentences":["采购完整方案可能加快上线，但也要考虑规则迁移。","如果编排规则无法导出，首版保留自研编排层就能减少日后重写核心流程的风险。"]}
```

#### 发言前证据检索

专家依据冻结实录区分普通贡献、复杂事实和前沿研究。普通贡献直接参与裁决。外查需同时启用 evidenceWindow、给出受控原因 `COMPLEX_FACT` 或 `FRONTIER`，以及 2–14 个英文公共关键词（最长 100 字符）。可用 searchPremise 从本项主张摘取至少 8 字限定核验范围。旧模板仅给关键词时按普通报名处理。

需要核验的专家保持待机。独立有界线程池先核对场内专家引文，必要时用 Crossref 检索和复查 DOI 元数据，再由证据技能评估原始摘要。服务端逐项核对元数据和引文后才将来源交给 R03。检索网络限时 8 秒，整个后台任务默认 12 秒，含排队。超时或无证据时，R03 只能依据实录作条件式表达。

查证结束才将该候选交给本窗裁决，其他就绪专家可以先发言。下一窗所有候选重新基于已提交实录报名，同一房间、专家、检索词与前提可复用查证材料。更换前提取消旧任务，收尾时取消剩余任务。`PANEL_AI_EVIDENCE_TIMEOUT_MILLIS` 设置后台时限，0 关闭查证。R04 仍要求本场至少两位不同专家的原文。

#### 校验分支与验收

1. **触发校验。** 只有有效非 `PASS` 候选能进入 R03。`ADD/REBUT` 的目标缺失、归属错误或超出本次引用集合时，在调用前放弃该候选。`RAISE/BUZZ` 的 `null` 目标合法。
2. **内容与写入。** 对句数、每句格式、总长度、安全和当前窗口版本做校验。通过后服务端沿用已绑定的说话人和回应目标，在同一事务提交 `EXPERT` 发言及其公开事件。成功提交才计入本阶段发言名额并触发 R04。
3. **失败分支。** 结构和可修正内容错误走 R08。补偿耗尽、内容拦截或任务过期时，丢弃正文并清理该任务对应的成员运行状态。已启动的报名窗口仍计数，由编排器按配额决定继续或收尾。
4. **验收。** T03 覆盖三句、两句合计超长、额外目标字段、非法绑定目标与旧回包。断言失败路径没有新增发言或提炼请求。Q02 对照绑定原文验证口播是否仍在回应同一主张，且提供了实际增量。检索测试使用工具替身，覆盖匹配原文、场内材料充分跳过、工具关闭、无匹配、超时、迟到和修正复用。

### R04｜直播共识与分歧

**任务标识** `R04`　**输出契约** `insightsOutput`　**触发条件** 每条专家发言成功提交后，对此版本触发一次逻辑提炼。  
**入参** `{discussionGoal,phase,topic,utterances,previousInsights,insightStatus,insightsThroughUtteranceSeq}`。`utterances` 覆盖该版本全部有效专家发言，`previousInsights` 是可随本次请求携带的上版结论。  
**任务目标** 用本场公开发言重算当前共识与分歧列表，每一条结论都能定位到支撑它的原文。解决 U03，支撑 F05。

[查看 Prompt 模板](./tasks/insights.md)

**正常示例**　两位专家都支持小流量试点，但对首版是否自研核心编排意见不同。`#2` 和 `#4` 对应产品设计中的同场公开实录。

```json
{"insights":[{"kind":"CONSENSUS","text":"先用小流量验证首次解决率","evidence":[{"utteranceSeq":2,"quote":"先在小流量中验证首次解决率"},{"utteranceSeq":4,"quote":"我支持用小流量验证首次解决率"}]},{"kind":"DISAGREEMENT","text":"首版应采购还是自研核心编排","evidence":[{"utteranceSeq":2,"quote":"先采购包含编排的完整方案"},{"utteranceSeq":4,"quote":"核心对话编排应从首版就由团队自研"}]}]}
```

**证据不足示例**　全量实录只有一位专家给出主张，其他成员还未明确表态。

```json
{"insights":[]}
```

#### 校验分支与验收

1. **强校验。** 按本房间、冻结版本和实际发送的引用集合校验 `utteranceSeq`。再核对专家角色、独立说话者数量、引文是入库原文的精确子串、条数上限及重复结论。Q03 用完整原文评估语义关系，覆盖逐字引用但删掉否定或错合条件的情形。
2. **有效结果分支。** 整组输出通过才原子替换现有投影及其证据，状态为 `FRESH`，来源游标推进到本次完整提炼覆盖的最新专家发言号。完整输入但证据不足时，空数组也是有效结果。
3. **暂缓与过期分支。** 核心实录缺失或超限、内容被拦截、输出补偿后仍无效时，保留上一次有效投影及来源游标，发布 `STALE`。版本过期的回包直接丢弃，避免覆盖新投影或发送旧的暂缓事件。
4. **验收。** T04 覆盖同人双证据、错引原文、未来和跨房间引用、合法空投影、暂缓恢复。Q03 核对范围、原文语义和立场撤回。E03 断言直播结束前能看到更新。

### R05｜主持开场

**任务标识** `R05`　**输出契约** `utteranceOutput`　**触发条件** 用户确认阵容后，后台取得当前房间的开场执行权。  
**入参** `{discussionGoal,phase,topic,host,perspectives}`，其中 `phase=OPENING`。题目和目标取自本场已保存的草稿。  
**任务目标** 用中立的口播说明本场要解决什么问题，并提出可由不同专家回答的首个问题。解决 U01，支撑 F03。

[查看 Prompt 模板](./roles/host-opening.md)

**评估开场示例**　题目未给定上线时间，主持邀请专家说明各自考虑的条件。

```json
{"sentences":["今天讨论中小团队该先自研还是采购 AI 客服。","请各位说明哪些条件会影响你们的选择，以及这些条件有什么依据？"]}
```

**排查开场示例**　题目仅确认接入后转人工率升高，开场先问对照数据。

```json
{"sentences":["本场讨论接入 AI 客服后转人工率升高的现象。","哪些数据可用于对照，其来源和口径分别是什么？"]}
```

#### 校验分支与验收

1. **触发与强校验。** 核对本房间已确认、主持身份存在、阶段为 `OPENING` 且尚无已提交开场。校验句数、总长度、安全及任务版本，返回值只保留 `sentences`。明确替专家下判断或引入业务假设的候选按质量错误处理。
2. **成功与失败。** 成功时由服务端原子提交 `OPENING` 及事件，然后开启首个报名窗口。结构或可修正业务错误按 R08 补偿，最后失败则按现有房间失败规则处理。缺少主持、题目或有效执行权时按相应上下文或过期规则处理。
3. **验收。** T07 断言开场先于报名，重复响应不会再写一条开场，失败时不会创建报名窗口。用同主题的评估和排查样本核查首问是否分别指向评价标准与现象对照。

### R06｜主持追问与串联

**任务标识** `R06`　**输出契约** `interventionOutput`　**触发条件** 编排器按阶段计划触发串联，或有有效 `PASS` 但无人获选时触发追问。  
**入参** `{discussionGoal,phase,mode,topic,host,utterances,insights,insightStatus,insightsThroughUtteranceSeq}`。`mode` 由服务端指定为 `BRIDGE` 或 `FOLLOW_UP`，`phase` 指向要开展或重新尝试的阶段。  
**任务目标** 将当前讨论接到下一阶段，或把原问题缩到可立即继续回答的范围。解决 U01、U02，支撑 F03。

[查看 Prompt 模板](./roles/host-intervention.md)

**串联示例**　`mode=BRIDGE`，发言 `#3` 提出在采购合同中加入退出条款。主持将话题从合同成本引向迁移约束。

```json
{"sentences":["陈简提出在采购合同中加入退出条款。","你们依据哪些材料判断迁移约束会如何影响这项建议？"],"replyToUtteranceSeq":3}
```

**追问示例**　`mode=FOLLOW_UP` 且只有排查开场。主持缩小观察范围，回应目标为空。

```json
{"sentences":["哪些数据能反映接入前后的转人工变化？"],"replyToUtteranceSeq":null}
```

#### 校验分支与验收

1. **触发与引用。** 由服务端检查 `mode`、剩余主持次数、阶段和预算。缺少合格专家目标时省略 `BRIDGE`。`FOLLOW_UP` 有目标时核对本房间专家和冻结输入中的引用集合。校验口播和目标后，用服务端选定的 `BRIDGE` 或 `FOLLOW_UP` 类型写实录与事件。
2. **失败分支。** 已启动的中途主持任务按已有规则消耗一次逻辑额度。可修正的格式、目标或可确认的主持越界按 R08 处理，最终失败不写发言，由编排器继续或收尾。超期结果丢弃。
3. **验收。** T07 覆盖 `BRIDGE` 空目标、`FOLLOW_UP` 合法空目标、主持冒充专家引用、跨场或过期引用以及额度耗尽。Q02 检查串联是否准确承接原话，以及追问是否指向可回答的问题。

### R07｜主持总结

**任务标识** `R07`　**输出契约** `summaryOutput`　**触发条件** 类型阶段执行结束、讨论无法继续推进或达到收尾边界，房间进入 `SUMMARIZING`。  
**入参** `{discussionGoal,phase,mode,topic,host,utterances,insights,insightStatus,insightsThroughUtteranceSeq}`。`phase=SUMMARY`，`mode` 由服务端指定为 `WITH_EXPERT_INPUT` 或 `LIMITED`。  
**任务目标** 按讨论类型生成两句主持口播，归纳专家已明确表达的观点、共识范围、未决分歧与证据缺口，并提供可核验的内部引用。解决 U03，支撑 F07。

[查看 Prompt 模板](./roles/host-summary.md)

**有专家发言示例**　`mode=WITH_EXPERT_INPUT`，`#2/#4` 都说应先以小流量验证首次解决率，对首版核心编排保留不同选择。

```json
{"sentences":["两位发过言的专家都建议先用小流量验证首次解决率。","陈简倾向采购完整方案，林昭倾向自研核心编排，双方对首版方案仍有分歧。"],"evidenceUtteranceSeqs":[2,4]}
```

**有限总结示例**　`mode=LIMITED`，实录不足以做具体归因或确认根因。

```json
{"sentences":["目前的专家发言不足以判断转人工率升高的原因。","接入前后的转接率是否采用同一统计口径，仍待专家说明。"],"evidenceUtteranceSeqs":[]}
```

#### 校验分支与验收

1. **模式与证据。** 按不同有效专家数选择模式。少于两位使用 `LIMITED`，其余使用 `WITH_EXPERT_INPUT`。核对句数、总长度、引用去重、专家身份、房间、冻结版本和本次引用集合。只要句中出现对具体专家的判断、建议、倾向或证据描述，证据就不能为空，不按动词区分。可确认的主持自作业务判断、站队或添造结论按质量错误处理，归因与证据是否充分由 Q04 检验。
2. **成功提交。** 将验证通过的正文写为 `SUMMARY` 发言。本事务先追加总结事件，再提交 `COMPLETED` 和相应状态事件。公开实录使用自然语言正文，证据数组用于入库前核验。
3. **失败分支。** 在总结预留预算内对可修正错误应用 R08。补偿后仍然失败时进入 `FAILED`，保留已经提交的实录与观点。总结或终态事务失败时回滚整笔提交。
4. **验收。** T07 覆盖正常收尾、有限总结、错误引用、重复回包及总结事务回滚。E01/E05 验证完成顺序与失败回看。Q04 验证归因强度、旧观点撤回和两句话是否忠实归纳专家意见、证据和未决分歧。

### R08｜有界契约修正

**触发与契约**　同一逻辑调用的首次结果不合格，且物理调用额度和截止时间仍允许一次补偿。使用原任务、原快照、相同引用集合与原 Schema。仅添加服务端生成的 `validationCodes`，按下表优先级去重及排序。同一级按表中列举顺序。解析失败时只发送 `JSON_INVALID`，字段不可读取时只记录可可靠定位的结构问题。

| 优先级 | 编号 | 修正要求 |
| --- | --- | --- |
| 1 | `JSON_INVALID`、`SHAPE_INVALID`、`OUT_OF_RANGE` | 重建完整任务对象，先满足字段、类型、数量和长度上限 |
| 2 | `INVALID_TARGET`、`INVALID_QUOTE`、`INVALID_EVIDENCE`、`UNSUPPORTED_CLAIM` | 修正引用归属、精确引文及证据和主张关系。证据不足时用任务允许的空结果或有限表达 |
| 3 | `PERSPECTIVE_DUPLICATE`、`LOW_QUALITY` | 专家任务生成有实际差异的立场或新贡献。主持任务去除自行判断、假设、倾向性提问和结论，保留中立引导或有归属的转述。无法补充时按原任务降级 |
| 4 | `INVALID_SENTENCES` | 控制句数与口播格式，并复核前面各项约束 |

R01 的阵容业务校验另按目标枚举、请求人数、首项主持、主持 `stance`/`perspective` 为空、角色、视角唯一、立场实质差异、规范化姓名唯一和字段长度复核。修正请求按这些字段整体重写，不能只修补一处。`GOAL_MISSING`、`GOAL_INVALID`、`PARTICIPANT_COUNT`、`HOST_NOT_FIRST`、`HOST_COUNT`、`HOST_FIELD_INVALID`、`ROLE_INVALID`、`PERSPECTIVE_INVALID`、`STANCE_INVALID`、`NAME_DUPLICATE`、`FIELD_LENGTH_INVALID` 与 `LOW_QUALITY` 属于这一类校验编号。网关只透传 `SHAPE_INVALID` 时，修正模板仍按上述字段整体自查。

[查看 Prompt 模板](./tasks/repair.md)

传输超时、`429` 或可重试的 `5xx` 允许一次原请求重试。两种补偿共用一次额外机会，均计入调用预算，并受同一逻辑截止时间约束。配置、鉴权、上下文、内容拦截及版本过期不触发 R08。修正请求仅携带可信错误编号，舍弃旧模型输出和供应商错误正文。再次失败直接走该任务的降级分支。T08 覆盖多编号排序、传输后再结构失败、重复或迟到回包，以及补偿耗尽。

## 失败分类与降级

| 内部分类 | 可复核的判定 | 处理 |
| --- | --- | --- |
| `FORMAT_INVALID` | JSON 解析或 Schema 失败，例如额外 `status` 字段 | 预算允许时走一次 R08。再次失败进入对应任务降级 |
| `EVIDENCE_INVALID` | 结构正确但引用集合、归属、原文或可验证的事实约束失败 | 仍有有效上下文时可用 R08，错误码为可信枚举 |
| `QUALITY_LOW` | 结构与引用合法，但可确定地重复立场、复述已有观点或使用空洞的占位话术 | 用 Q01–Q04 的确定性断言识别。预算允许时用 `LOW_QUALITY` 或 `UNSUPPORTED_CLAIM` 修正一次，之后降级 |
| `CONTEXT_UNAVAILABLE` | 必填角色、来源或证据缺失，必留项超出预算 | 进入当前任务降级。数据尚未提交时等待对应业务步骤，而不是请求模型补造 |
| `CONTENT_BLOCKED` | 确定的隐私、凭据或内容风险 | 丢弃响应，进入当前任务降级，监测只记录规则和计数 |
| `STALE_RESPONSE` | 步骤关闭、版本不一致、重复回包或已超时失去提交权 | 丢弃，当前版本的任务独立推进，不产生业务记录或事件 |
| 上游不可用或超时 | HTTP、超时或鉴权失败 | 瞬时错误按 R08 段协议重试。对外沿用已有 HTTP 与业务码，维护内部原因分类 |

输入按任务校验。要求传 `utterances` 的任务以 `[]` 表示确实没有发言。字段缺失、为 `null` 或包含无法验证的必留记录时按上下文不可用处理。记录的 `participantId`、`seq`、`role`、`kind`、`content` 必须完整，`replyToUtteranceSeq` 可按任务为空。角色卡姓名必填。主持的 `stance`、`perspective` 均为 `null`，专家两个字段均必填且非空。开场已提交但尚无专家发言，是正常直播状态。表中固定文案由应用提供。失败阶段无法从已有状态确定时，房间状态区显示「讨论暂时无法继续」，若已有实录则同时提供查看入口。

| 任务 | 合法空输入或缺失场景 | 解析、质量或依赖故障最终处理 |
| --- | --- | --- |
| R01 阵容 | 不需要实录。主题缺失或脱敏后为空，返回 `400`，提示「请输入一个具体的讨论议题」 | `502` 用于无效阵容或上游调用失败，超时沿用 `504`。表单保留有效输入，展示「暂时无法生成合格的专家阵容。可以重试，或从示例议题开始。」仅在用户主动选择预设后使用其阵容。失败不创建 `DRAFT` |
| R02 报名 | 只有开场或没有可追加贡献时，模型可返回下面的 `PASS`。尚未提交开场时暂不调度。专家身份缺失记为该候选失败 | 忽略失效候选并清除状态。按阶段规则处理有效 `PASS`、整窗故障和全场预算收尾。模型故障独立计量 |
| R03 发言 | 合法 `RAISE/BUZZ` 的目标为空。`ADD/REBUT` 缺已锁定的目标时跳过该候选 | 释放成员 `SPEAKING`，不写台词。在剩余窗口预算内继续，或交回编排器收尾。前端使用真实状态事件，不生成假发言 |
| R04 提炼 | 完整实录不足两位专家支持时允许 `{"insights":[]}`。可由应用按确定性规则生成这一空结果。已入库实录有足够覆盖但本次核心切片缺失时走 `STALE` | 发送保留旧投影的 `STALE` 事件，显示「观点更新暂缓」。旧投影为空时显示暂缓空态。来源游标保持不动，下一条专家发言后可恢复 |
| R05 开场 | 不需要实录。经确认的主持或主题缺失，按房间上下文错误处理 | 进入 `FAILED`，提示「主持开场暂时无法生成」。没有成功提交开场时不进入报名 |
| R06 追问或串联 | 没有专家发言时，仅在已提交开场的前提下允许 `FOLLOW_UP`，目标为 `null`。`BRIDGE` 无有效目标时省略 | 不写占位追问。允许编排器按已有窗口次数决定继续或收尾 |
| R07 总结 | 完整上下文中不足两位专家时使用 `LIMITED`。只在摘要不归因具体专家时允许空引用。例如下面的两句有限总结 | 总结依赖或质量失败后进入 `FAILED`，提示「暂时无法生成可靠总结，已保留讨论实录」。错误提示只属于房间状态区，不当作主持总结发布 |
| R08 修正 | 复用可验证的原输入。缺快照、只有风险内容或预算用尽时，直接处理当前任务降级 | 不再追加模型请求。对外行为、错误提示和写入边界由原任务决定 |
