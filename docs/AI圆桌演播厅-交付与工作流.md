## 1. 作业规则与硬性交付清单

原文要求一人用一款 Vibe Coding 工具从零开发，主体开发在该工具中进行，按阶段使用多个 Prompt。技术硬约束为 SQLite、前后端分离、后端环境变量存放模型 API Key、实时传输、隔离的并行房间、中文响应式和独立区域滚动。

| 交付项 | 原文要求 | 最终文件或证据 |
| --- | --- | --- |
| 完整源码及仓库链接 | 提交 GitHub 或 Gitee 链接，仓库含完整代码和可观察的演进历史 | `frontend/`、`backend/`、`e2e/` 或等价目录；仓库链接与评审可用权限；ZIP 对应清晰的提交或标签 |

## 3. 72 小时实施顺序与阶段门槛

时间为相对收到作业的建议排期，提交历史跟随真实产出。建议每次 Prompt 只服务一个可验收改动。

| 时间窗口 | 阶段与 Prompt | 阶段完成条件 | 提交主题示例 |
| --- | --- | --- | --- |
| 0–8 小时 | SDD，P01–P02 | 完成要件清单、用户路径、ER 和状态机、API/SSE 规格；验证主体工具能工作 | `docs: 定义产品范围与 SQLite 模型`、`docs: 冻结 API 和事件契约` |
| 8–20 小时 | DDD，P03–P04 | Vue 3 使用契约 fixture 走通大厅、预览、演播厅，测试同一会话的 SSE 故障、重连和释放，保存实际视口验证 | `feat(ui): 完成 Vue 大厅、阵容和演播厅组件` |
| 20–47 小时 | TDD，P05–P08 | 阵容、调度、结论的测试按实际顺序从失败到通过；SQLite 迁移和并行 SSE 联调完成；预设可用 | `test: 覆盖候选调度和终止条件`、`feat: 实现讨论编排与失效恢复` |
| 47–62 小时 | E2E，P09–P10，必要时 P12 | 真实前后端通过主链路、直播更新、两个房间、重连、异常和三视口；记录一次真实模型烟测结果 | `test(e2e): 覆盖实时讨论、重连和隔离`、实际修复提交 |
| 62–72 小时 | 交付复核，P11 | 干净环境按 README 重跑；完结核心 Prompt 记录、工作流说明、ZIP 和仓库邀请；核对时间和访问权限 | `docs: 完成运行、测试与交付说明` |

优先验证主链路、实时结论、跨房间隔离和三种核心逻辑的 Red/Green。用测试网关进行重复验证，用真实模型检查语义和耗时。完整正常路径的基础模型调用量为 `专家发言数 × (专家人数 + 2) + 开场和总结各 1 次 + 0–3 次中途主持`。默认 4 位专家时，三阶段的 10 条专家发言为 62–65 次，另计创建阶段阵容请求。失败、无人报名、补偿和可选检索产生的模型调用也计入额度，整场最多 112 次物理模型请求。采集各任务的真实输入/输出 token 和供应商单价，再核对工具额度。单场耗时和费用以真实运行数据为准。

## 4. 核心 Prompt 归档与工作流说明模板

### 核心 Prompt 归档

每轮保存发送时的原文和当时使用的附件版本。评审文档选取影响关键设计或修复的至少 5 段，且四阶段齐全。以一条可核对的事实记录 1–2 句说明，包含当时意图、遇到的挑战或如何修正。每段附代码提交或运行结果位置，以便追溯。

```markdown
### 【TDD 阶段】调度优先级

工具和模型：[实际工具、模型标识]
关联规格：[T02 及规格版本]
原始 Prompt：[逐字记录已发送内容，敏感凭据用统一脱敏标记]
说明：[用 1–2 句记录意图和实际发现或修正]
证据：[Red / Green 的提交号、测试名或命令记录]
```

### 1–1.5 页工作流说明提纲

**开发方式**。我使用 `[实际工具与模型名称]` 完成 `[实际完成的主体开发环节]`。我首先把 `[作业要求]` 转成 `PRD、schema、API/SSE`，再将契约交给前端组件轮次；核心逻辑用实际失败的测试限制实现范围，最后通过 `[测试命令与结果]` 校验。开发工具与应用运行时模型的实际接入分别是 `[配置方式及模型标识，去除凭据]`。

**典型问题与解决路径**。从下列候选中只选实际出现的问题，或换成其他有证据的问题。每例用 3–5 句写清复现、根因、修复和验证。

| 候选问题 | 复盘时需记录的真实证据 |
| --- | --- |
| 专家输出看似抢答，实录始终按固定顺序 | 保存一段模型候选与实际顺序，指出是否由模型输出或编排逻辑导致；列出改动和对应调度测试 |

| SSE 断线或切房后重复、遗漏、串房 | 保留两路房间 ID 和游标，说明后端回放还是前端订阅处理有问题，附 E02/E04 修复验证 |

**工程化 AI 开发理解**。用一个实际案例说明如何把需求转成可检验的契约、让 AI 在明确范围内改动，通过测试和浏览器证据判断结果，并说明自己作出的决定与取舍。列出真实模型验证结果及仍存在的限制。提交前检查预览或打印页数，保持 1–1.5 页。

本清单随作业范围、仓库结构或最终投递信息变更而更新。测试命令、提交号、产物链接、工具与模型标识以实际记录为准。
