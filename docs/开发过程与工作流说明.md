# 3. 开发过程思路 & 工作流说明

> 工具说明：本项目未使用 Claude Code + DeepSeek V4 Pro。实际分工为 **Codex 负责方案设计与主体开发，DS Harness 与 Trae 负责问题定位、验证与修复**。

## 3.1 开发流程：Codex +GPT6.2系列模型主导设计开发，DS Harness + Trae 辅助攻坚

项目按“先契约、后实现、再验收”推进，避免让 AI 自由发挥。

1. **需求与规格**：先读作业原文，把硬约束拆成三份可执行文档：产品与工程设计（状态机、SQLite 模型、HTTP/SSE 协议）、分阶段开发 Prompt（SDD/DDD/TDD/E2E 任务卡）、运行时契约（`docs/runtime-contract.schema.json`）。`AGENTS.md` 把这些文档固化为仓库级规则，后续每次对话都以此为上下文，减少 AI 偏题。
2. **主线开发用 Codex**：以阶段为单位提交 Prompt（大厅与预设 → 阵容 → 演播厅与 SSE → 发言调度与提炼 → 收尾与异常路径），每轮只允许改一个纵向切片，并要求回报“改动文件、执行命令、实际结果、未验证项”。Codex 负责主体代码生成与重构，我负责架构决策、契约审定和结果验收。
3. **问题攻坚用 DS Harness + Trae**：涉及跨层联调、运行时行为不确定的问题（超时、SSE 重连、浏览器布局），先用 DS Harness 做小范围复现与参数验证，再由 Trae 在仓库内定位调用链、补测试并修复。提交前的安全与错误审查同样由 Trae 完成，产出 `docs/security-review-full-repo-2026-11-21.md`。
4. **质量闸门**：前端 `vue-tsc` + Vitest（31 项，全部通过），后端 JUnit + 临时 SQLite 集成测试覆盖调度、提炼、异常与数据隔离；E2E 用 Playwright 验证真实前后端链路，覆盖两场并行、直播中更新结论、断线重连与跨房间迟到事件，并在 1920×1080、1366×768、390×844 三种视口验收；真实模型的质量与耗时单独记录，不混入自动化断言。

## 3.2 与 AI 协同中的两个典型问题及解决路径

### 问题一：长讨论的上下文管理与幻觉控制

- **现象**：讨论进入中后段后，模型开始引用不存在的发言序号，或把 A 的立场安到 B 头上；若把全量实录直接塞进上下文，又会 Token 超限、耗时陡增，提炼任务连续超时。
- **根因**：① 上下文没有边界，历史越长注意力越稀释，截断位置不可控；② “引用哪条发言”由模型自己在文本里声明，服务端没有核验；③ 外部检索结论与模型陈述之间缺少逐字比对，模型容易补全不存在的文献。
- **解决路径**（四层约束）：
  1. **输入侧窗口化**：`ContextSlice` 按 Token 预算动态装配上下文，且保证必选内容不丢——主持人当前问题、本轮回应目标、完整回复链、最近两条专家发言；历史结论只有在证据序号仍在窗口内时才纳入，并自动补全其引用链，装不下就整条丢弃，绝不硬塞。
  2. **输出侧契约化**：所有模型输出先过 JSON Schema，再过业务校验；公开 DTO 只映射白名单字段，隐藏推理字段直接丢弃，报名分数、模型原始响应不进入公开接口。
  3. **引用落地校验**：共识结论的证据必须是本窗内真实的专家发言序号，序号去重、引文必须是原句的逐字子串（`line.content().contains(quote)`），且至少覆盖两位不同专家；不满足即判 `INVALID_EVIDENCE` / `INVALID_QUOTE`，触发一次带错误码的修复重试，仍失败则保留上一版并标记 `STALE`。
  4. **外部查证可核验**：学术证据要求 DOI、标题、作者、年份、期刊五项与 Crossref 返回完全一致，摘要需包含 ≥12 字符原文片段才接受；任何一项对不上就丢弃，宁可没有证据也不补造。
  5. **预算与超时兜底**：全场最多 112 次模型请求，预留 2 次给总结；单次 10s（即时提炼 28s），格式错误最多修复一次，避免“无限自我纠正”拖垮整场。
- **验证**：长讨论复跑中，结论引用的每条证据都能回查到具体发言与原句；提炼失败时界面明确显示 `STALE`，不会出现“看起来有结论但无法追溯”的情况。

### 问题二：核心业务规则不能交给模型决定

- **现象**：R01 生成阵容时出现视角重复、立场空泛、主持人被赋予立场；多专家同时报名导致同一人连续刷屏、`PASS` 被当成一次发言；结论只有单一专家观点，或引用了窗口外的发言。
- **根因**：把“谁先说、引用哪条、结论是否成立”交给模型判断，而模型的输出天然不稳定且不可审计。正确做法是模型只提供候选与理由，规则由服务端裁决。
- **解决路径**（三条核心链路分别下沉规则）：
  1. **嘉宾生成**：Schema 约束结构后，`RosterValidator` 再校验专家数量符合请求且不超过 6 位、视角必须来自固定枚举且不重复、立场长度 8–100 字、主持人的 `stance/perspective` 必须为 `null`；不通过带错误码重试一次，仍失败返回 503，不落半成品 `DRAFT`。
  2. **发言调度**：模型只提交“意愿 + 意图 + 关注点 + 查证线索”，顺序由 `BidArbitrator` 统一裁决：过滤 `PASS`；同一专家连续发言两次后必须让位；有查证窗口时优先可检索候选；评分 = 意图权重（反驳 3、补充/附和 2、其他 1）+ 是否命中当前焦点 + 距上次发言越久加分；同分按上次发言位置与 ID 稳定排序，保证结果可复现。
  3. **共识提炼**：`LiveInsightService.validate` 强制证据来自本窗专家发言、序号去重、原文逐字匹配、至少两位专家；同类结论最多 3 条且文本去重；失败保留旧版并标 `STALE`。主持收尾只归纳可追溯的观点，结论入库后才允许置为 `COMPLETED`。
- **验证**：三条规则各有单测覆盖——非法阵容组合、连续发言强制让位、证据不足或引文不匹配；测试用脚本网关替换真实模型，确保结论不依赖模型随机性。

## 3.3 对“工程化 AI 开发”的理解

1. **AI 产出是候选实现，不是结论**。人负责架构、契约和验收标准；AI 负责在边界内快速产出代码。没有可执行的契约（状态机、Schema、错误码），AI 生成得越快，返工越大。
2. **契约先行、测试兜底**。先定接口与数据契约，再让 AI 实现；用失败断言驱动修复，而不是“看起来对”。本项目所有模型输出都先过 JSON Schema，再过引用归属、原文匹配、发言长度等业务校验。
3. **把不确定性当常态设计**。模型会超时、会返回脏结构、会幻觉引用，所以要有超时、重试、修复提示、请求预算、事务外调用、`STALE` 降级和幂等启动，而不是假设一次成功。
4. **成本、并发与安全属于工程边界**。有界工作池、模型 I/O 池、SSE 连接上限、Token 预算、PII 双向拦截、本机 Host/Origin 校验，这些不是“优化项”，是上线门槛。
5. **可观测与可追溯**。日志记录跟踪 ID、房间、任务、模板版本与结果，过滤密钥和模型原始响应；Prompt 与测试证据纳入版本管理，才能复盘“哪次改动让质量变差”。
6. **使用AI开发最关键的一点是：**选用优质模型。优质模型可以省去部分调优时间，特别是对于需要高强度推理的业务，选用优质模型不仅能保证输出质量，还能稳定支撑复杂指令遵循、结构化输出等需求，降低 Prompt 工程、结果校验与重试的开发成本，减少后续纠错、清洗、重跑的开销；同时在 JSON Schema 约束、多轮对话、长文档理解这类场景下，优质模型的服从性更强，更容易稳定输出符合契约规范的结果，减少业务侧异常兜底逻辑的开发工作量。

一句话总结：工程化 AI 开发的核心不是“让 AI 多写”，而是**用契约约束输出、用测试验证结果、用边界兜住失败、用证据支撑交付**。
